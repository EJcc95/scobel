# MySQL multi-tenant backend

Better Auth identifies the user; Express owns authorization. The frontend may
select an active organization for UX, but the server verifies membership on
every protected operation.

## Core tables

```sql
CREATE TABLE organizations (
  id CHAR(36) PRIMARY KEY,
  name VARCHAR(160) NOT NULL,
  slug VARCHAR(160) NOT NULL UNIQUE,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
);

CREATE TABLE memberships (
  organization_id CHAR(36) NOT NULL,
  user_id VARCHAR(64) NOT NULL,
  role ENUM('owner', 'admin', 'member') NOT NULL DEFAULT 'member',
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (organization_id, user_id),
  INDEX memberships_user_idx (user_id),
  CONSTRAINT memberships_org_fk FOREIGN KEY (organization_id)
    REFERENCES organizations(id) ON DELETE CASCADE
);
```

Every tenant table includes `organization_id` plus an index. Use the exact user
id type generated by Better Auth in the real migration.

## Express authorization

```ts
export async function requireOrgRole(userId: string, orgId: string, roles: string[]) {
  const membership = await membershipRepository.find(userId, orgId);
  if (!membership || !roles.includes(membership.role)) {
    throw new HttpError(403, "forbidden");
  }
  return membership;
}
```

Call it after session validation and before the service mutation. Prefer a
transaction when changing membership plus organization-owned data.

## Invites

Store `token_hash`, never the raw token. On acceptance, validate expiry, match
the authenticated email according to product rules, insert membership, and
consume the invite atomically. Never log invite tokens.

## Checklist

- [ ] Every tenant query scopes by a server-derived organization id.
- [ ] Every protected route validates Better Auth session and membership.
- [ ] User A cannot read or mutate organization B.
- [ ] Role changes and ownership transfer have explicit flows.
- [ ] Invite acceptance is transactional and server-mediated.
